# 기능 명세서: GitHub 기반 테크 블로그

**기능 브랜치**: `001-github-jekyll-chirpy`
**작성일**: 2025-10-15
**상태**: 초안
**입력**: 사용자 설명: "GitHub 기반 테크 블로그를 Jekyll + Chirpy 테마로 구축. 최대한 간단하게 설정하고, Markdown으로 포스트 작성, 카테고리/태그 시스템, 다크모드, 검색 기능 포함. GitHub Pages로 자동 배포."

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 기본 블로그 설정 및 배포 (우선순위: P1)

블로그 운영자는 복잡한 설정 없이 GitHub 저장소에 블로그를 생성하고, GitHub Pages를 통해 자동으로 온라인에 공개할 수 있어야 합니다. 운영자는 블로그 제목, 설명, 작성자 정보 등 기본적인 메타데이터를 설정할 수 있어야 합니다.

**이 우선순위를 선택한 이유**: 블로그의 핵심 인프라를 구축하는 단계로, 이것 없이는 다른 모든 기능이 작동할 수 없습니다. 이 단계만 완료되어도 블로그가 온라인에 공개되어 방문 가능한 상태가 됩니다.

**독립 테스트**: Chirpy 테마가 적용된 블로그가 GitHub Pages URL을 통해 접속 가능하고, 설정한 제목과 설명이 홈페이지에 표시되는지 확인함으로써 완전히 테스트 가능합니다.

**승인 시나리오**:

1. **주어진 상황** GitHub 계정이 있고 블로그를 만들고 싶은 사용자, **행동** Chirpy Starter 템플릿을 사용하여 새 저장소를 생성하고 기본 설정 파일을 수정, **그러면** 브라우저에서 `username.github.io` 주소로 블로그에 접속할 수 있고 Chirpy 테마의 기본 레이아웃이 표시됨
2. **주어진 상황** 블로그 설정 파일이 열려 있는 상태, **행동** 블로그 제목을 "나의 기술 블로그"로, 설명을 "개발 여정을 기록하는 공간"으로 설정, **그러면** 홈페이지 상단에 설정한 제목과 설명이 정확하게 표시됨
3. **주어진 상황** 블로그 저장소에 변경사항 커밋, **행동** GitHub에 푸시, **그러면** 1-2분 내에 변경사항이 자동으로 GitHub Pages에 반영되어 라이브 사이트에서 확인 가능

### 사용자 스토리 2 - 포스트 작성 및 관리 (우선순위: P1)

블로그 운영자는 Markdown 형식으로 기술 포스트를 작성하고, 작성한 포스트가 블로그 메인 페이지에 최신순으로 자동 정렬되어 표시되는 것을 확인할 수 있어야 합니다. 각 포스트에는 제목, 작성일, 요약 등의 메타데이터를 포함할 수 있어야 합니다.

**이 우선순위를 선택한 이유**: 블로그의 핵심 목적은 콘텐츠를 작성하고 공유하는 것입니다. 포스트 작성 기능 없이는 블로그가 의미가 없으므로 최우선 순위입니다.

**독립 테스트**: 특정 형식의 Markdown 파일을 생성하여 저장소에 커밋한 후, 블로그 메인 페이지에서 해당 포스트가 올바른 형식으로 표시되고 클릭 시 전체 내용을 볼 수 있는지 확인함으로써 테스트 가능합니다.

**승인 시나리오**:

1. **주어진 상황** `_posts` 폴더에 `2025-10-15-my-first-post.md` 파일을 생성, **행동** Front matter(제목, 날짜 등)와 본문 내용을 Markdown으로 작성하고 커밋, **그러면** 블로그 홈페이지에 포스트가 최상단에 표시되고 클릭 시 전체 내용이 렌더링됨
2. **주어진 상황** 기존에 3개의 포스트가 있는 상태, **행동** 더 최근 날짜로 새 포스트를 추가, **그러면** 새 포스트가 목록 최상단에 표시되고 나머지는 작성일 역순으로 정렬됨
3. **주어진 상황** 포스트 본문에 코드 블록, 이미지, 링크가 포함된 상태, **행동** 포스트 페이지 접속, **그러면** 코드는 Syntax Highlighting이 적용되고, 이미지는 정상 로드되며, 링크는 클릭 가능한 상태로 표시됨

### 사용자 스토리 3 - 카테고리 및 태그 시스템 (우선순위: P2)

블로그 운영자는 각 포스트에 카테고리와 태그를 지정할 수 있으며, 방문자는 카테고리 페이지와 태그 페이지를 통해 관련 포스트들을 필터링하여 볼 수 있어야 합니다.

**이 우선순위를 선택한 이유**: 포스트가 많아질수록 콘텐츠 분류가 중요해지지만, 초기에는 포스트 개수가 적어 분류 없이도 탐색 가능합니다. 하지만 장기적인 콘텐츠 관리를 위해 초기부터 구조를 갖추는 것이 좋습니다.

**독립 테스트**: 여러 포스트에 서로 다른 카테고리와 태그를 지정한 후, 카테고리 페이지와 태그 페이지에서 해당 분류에 속한 포스트들만 필터링되어 표시되는지 확인함으로써 테스트 가능합니다.

**승인 시나리오**:

1. **주어진 상황** 포스트 Front matter에 `categories: [Backend, Python]`으로 설정, **행동** 사이드바에서 Categories 메뉴 클릭, **그러면** "Backend"와 "Python" 카테고리가 목록에 표시되고, 각각 클릭 시 해당 카테고리의 포스트만 필터링됨
2. **주어진 상황** 포스트에 `tags: [django, api, rest]` 설정, **행동** 포스트 하단의 태그 클릭 또는 Tags 페이지 접속, **그러면** 해당 태그가 부여된 모든 포스트가 날짜순으로 나열됨
3. **주어진 상황** 10개의 포스트가 3개의 서로 다른 카테고리로 분류된 상태, **행동** 특정 카테고리 선택, **그러면** 해당 카테고리에 속한 포스트 개수가 정확히 표시되고 포스트 목록이 올바르게 필터링됨

### 사용자 스토리 4 - 다크모드 지원 (우선순위: P2)

블로그 방문자는 사이트 상단의 토글 버튼을 통해 라이트 모드와 다크 모드를 전환할 수 있어야 하며, 선택한 테마 설정이 브라우저에 저장되어 다음 방문 시에도 유지되어야 합니다.

**이 우선순위를 선택한 이유**: 사용자 경험을 향상시키는 중요한 기능이지만, 블로그의 핵심 기능(콘텐츠 읽기)은 다크모드 없이도 작동합니다. Chirpy 테마는 기본적으로 다크모드를 지원하므로 추가 작업이 최소화됩니다.

**독립 테스트**: 브라우저에서 블로그를 열고 다크모드 토글 버튼을 클릭한 후 페이지 배경과 텍스트 색상이 변경되는지, 그리고 새로고침 후에도 설정이 유지되는지 확인함으로써 테스트 가능합니다.

**승인 시나리오**:

1. **주어진 상황** 라이트 모드로 블로그에 접속한 상태, **행동** 상단 네비게이션 바의 다크모드 토글 아이콘 클릭, **그러면** 배경이 어두운 색으로 변경되고 텍스트는 밝은 색으로 변경되며, 모든 UI 요소가 다크 테마에 맞게 조정됨
2. **주어진 상황** 다크 모드가 활성화된 상태, **행동** 브라우저를 닫았다가 다시 블로그 접속, **그러면** 이전에 설정한 다크 모드가 자동으로 적용되어 표시됨
3. **주어진 상황** 다크 모드에서 포스트 내용 읽는 중, **행동** 스크롤하며 코드 블록과 이미지 확인, **그러면** 코드 블록은 다크 테마용 Syntax Highlighting이 적용되고, 이미지는 과도하게 밝지 않게 표시되어 눈의 피로를 최소화

### 사용자 스토리 5 - 검색 기능 (우선순위: P3)

블로그 방문자는 사이트 내 검색 기능을 통해 키워드로 포스트를 검색할 수 있어야 하며, 검색 결과는 제목과 본문 내용을 모두 포함하여 관련성 높은 순서로 표시되어야 합니다.

**이 우선순위를 선택한 이유**: 포스트 개수가 적을 때는 스크롤이나 카테고리 탐색으로 충분하지만, 콘텐츠가 많아지면 검색 기능이 필수적입니다. Chirpy 테마의 기본 검색 기능을 활용하므로 구현 부담이 적습니다.

**독립 테스트**: 여러 개의 포스트가 있는 상태에서 특정 키워드를 검색하고, 해당 키워드를 포함한 포스트만 결과에 표시되는지 확인함으로써 테스트 가능합니다.

**승인 시나리오**:

1. **주어진 상황** 사이드바에 검색 아이콘 또는 검색 바가 표시된 상태, **행동** 검색 창에 "Python" 키워드 입력, **그러면** 제목이나 본문에 "Python"이 포함된 모든 포스트가 목록으로 표시되고 각 결과에서 검색어가 하이라이트됨
2. **주어진 상황** 검색 결과 페이지에 여러 포스트가 나열된 상태, **행동** 검색 결과 중 하나 클릭, **그러면** 해당 포스트 전체 내용이 표시되고 검색어 부분으로 자동 스크롤되거나 하이라이트됨
3. **주어진 상황** 검색 창에 존재하지 않는 키워드 입력, **행동** 검색 실행, **그러면** "검색 결과가 없습니다" 메시지가 표시되고 전체 포스트 목록을 볼 수 있는 링크가 제공됨

### 사용자 스토리 6 - About 페이지 (우선순위: P3)

블로그 운영자는 자신의 소개, 기술 스택, 경력, 연락처 정보를 담은 About 페이지를 작성할 수 있어야 하며, 방문자는 네비게이션 메뉴를 통해 쉽게 About 페이지에 접근할 수 있어야 합니다.

**이 우선순위를 선택한 이유**: 블로그의 신뢰성과 개인 브랜딩에 중요하지만, 포스트 작성 및 읽기 기능이 우선입니다. 초기에는 간단한 소개만으로도 충분합니다.

**독립 테스트**: About 페이지 파일을 작성하고, 사이드바 또는 상단 메뉴에서 About 링크를 클릭하여 페이지가 정상 표시되는지 확인함으로써 테스트 가능합니다.

**승인 시나리오**:

1. **주어진 상황** `_tabs/about.md` 파일에 자기소개 내용 작성, **행동** 사이드바에서 "About" 메뉴 클릭, **그러면** 작성한 소개, 기술 스택, 연락처 정보가 Markdown 서식에 맞게 렌더링되어 표시됨
2. **주어진 상황** About 페이지에 소셜 미디어 링크(GitHub, LinkedIn 등) 추가, **행동** 링크 클릭, **그러면** 새 탭에서 해당 소셜 미디어 프로필이 열림
3. **주어진 상황** About 페이지에 프로필 사진 추가, **행동** About 페이지 접속, **그러면** 사진이 적절한 크기로 표시되고 페이지 레이아웃이 깨지지 않음

---

### 엣지 케이스

- **포스트 파일명 형식 오류**: 파일명이 `YYYY-MM-DD-title.md` 형식을 따르지 않을 때, 포스트가 빌드 시 무시되거나 오류 메시지가 생성되어야 함
- **Front matter 누락**: 필수 메타데이터(title, date 등)가 누락된 경우, 빌드 오류가 발생하거나 기본값이 적용되어야 함
- **카테고리/태그 한글 사용**: 한글 카테고리나 태그를 사용할 경우 URL 인코딩이 올바르게 처리되고 페이지가 정상 작동해야 함
- **대용량 이미지**: 매우 큰 이미지 파일이 포스트에 포함될 경우, 페이지 로딩 속도가 저하될 수 있으므로 이미지 최적화 가이드를 제공해야 함
- **빌드 실패**: GitHub Actions 빌드가 실패한 경우, 저장소의 Actions 탭에서 오류 로그를 확인할 수 있어야 하고 이전 버전의 사이트는 계속 유지되어야 함
- **동시 편집 충돌**: 로컬에서 작업 중인 파일을 다른 곳에서 수정하여 충돌이 발생한 경우, Git merge 도구로 해결 가능해야 함
- **빈 카테고리/태그**: 어떤 포스트에도 사용되지 않은 카테고리나 태그는 목록에 표시되지 않거나 "0개 포스트"로 표시되어야 함

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 블로그는 GitHub Pages를 통해 `username.github.io` 또는 커스텀 도메인으로 접근 가능해야 함
- **FR-002**: 블로그 설정 파일을 통해 블로그 제목, 설명, 작성자 정보, 타임존, URL, 소셜 미디어 링크를 설정할 수 있어야 함
- **FR-003**: 포스트는 `YYYY-MM-DD-title.md` 형식의 Markdown 파일로 작성되어야 하며, `_posts` 폴더에 저장되어야 함
- **FR-004**: 각 포스트는 Front matter에 최소한 제목(title)과 날짜(date)를 포함해야 하며, 선택적으로 카테고리, 태그, 작성자, 설명을 포함할 수 있어야 함
- **FR-005**: 블로그 홈페이지는 모든 포스트를 작성일 역순(최신순)으로 목록 형태로 표시해야 함
- **FR-006**: 각 포스트는 제목, 작성일, 요약(또는 첫 몇 줄), 카테고리, 태그 정보를 미리보기로 보여주어야 함
- **FR-007**: 포스트 본문에서 Markdown 문법(제목, 목록, 링크, 이미지, 코드 블록 등)이 올바르게 HTML로 렌더링되어야 함
- **FR-008**: 코드 블록은 언어별 Syntax Highlighting이 적용되어야 하며, 라이트/다크 모드 모두에서 가독성이 높아야 함
- **FR-009**: 각 포스트에 지정된 카테고리는 자동으로 카테고리 페이지에 수집되어 표시되어야 하며, 카테고리별 포스트 개수가 표시되어야 함
- **FR-010**: 각 포스트에 지정된 태그는 자동으로 태그 페이지에 수집되어 표시되어야 하며, 태그별 포스트 개수가 표시되어야 함
- **FR-011**: 카테고리 또는 태그를 클릭하면 해당 분류에 속한 포스트만 필터링하여 보여주는 페이지로 이동해야 함
- **FR-012**: 사이트 상단 또는 사이드바에 다크모드/라이트모드 전환 토글 버튼이 표시되어야 함
- **FR-013**: 다크모드 전환 시 배경색, 텍스트 색상, UI 요소 색상이 일관되게 변경되어야 하며, 가독성이 유지되어야 함
- **FR-014**: 사용자가 선택한 테마 설정(라이트/다크)은 브라우저의 로컬 스토리지에 저장되어 다음 방문 시에도 유지되어야 함
- **FR-015**: 검색 기능은 사이드바 또는 상단 네비게이션에서 쉽게 접근 가능해야 함
- **FR-016**: 검색은 포스트 제목과 본문 내용을 모두 대상으로 하며, 검색어를 포함한 모든 포스트를 결과로 반환해야 함
- **FR-017**: 검색 결과에서 검색어는 하이라이트되어 표시되어야 하며, 결과가 없을 경우 적절한 안내 메시지가 표시되어야 함
- **FR-018**: `_tabs/about.md` 파일을 통해 About 페이지를 작성할 수 있어야 하며, 사이드바 네비게이션에서 접근 가능해야 함
- **FR-019**: 사이드바 네비게이션은 Home, About, Categories, Tags, Archives 등의 주요 페이지 링크를 포함해야 함
- **FR-020**: 블로그는 데스크톱, 태블릿, 모바일 기기에서 모두 적절하게 표시되는 반응형 디자인이어야 함
- **FR-021**: GitHub 저장소에 변경사항을 푸시하면 GitHub Actions가 자동으로 트리거되어 빌드 및 배포가 수행되어야 함
- **FR-022**: 빌드 및 배포 프로세스는 사용자 개입 없이 자동으로 완료되어야 하며, 완료까지 일반적으로 1-2분 이내여야 함
- **FR-023**: 빌드 실패 시 GitHub Actions 로그에 오류 원인이 명확히 표시되어야 하며, 이전 버전의 사이트는 계속 운영되어야 함
- **FR-024**: RSS 피드가 자동으로 생성되어 `/feed.xml` 경로에서 접근 가능해야 하며, 최신 포스트 정보를 포함해야 함
- **FR-025**: 각 포스트 페이지는 소셜 미디어 공유를 위한 메타 태그(Open Graph, Twitter Card)를 포함해야 함

### 주요 엔티티

- **포스트 (Post)**: 블로그의 핵심 콘텐츠 단위로, 제목, 작성일, 본문 내용, 카테고리 목록, 태그 목록, 작성자 정보, 요약/설명을 포함함. 각 포스트는 고유한 URL을 가지며 Markdown 형식으로 작성됨
- **카테고리 (Category)**: 포스트를 주제별로 분류하는 계층적 구조. 하나의 포스트는 여러 카테고리에 속할 수 있으며, 카테고리 페이지에서 해당 카테고리의 모든 포스트를 조회할 수 있음
- **태그 (Tag)**: 포스트를 키워드 기반으로 분류하는 비계층적 레이블. 하나의 포스트는 여러 태그를 가질 수 있으며, 태그 페이지에서 해당 태그의 모든 포스트를 조회할 수 있음
- **블로그 설정 (Blog Configuration)**: 블로그의 전역 설정 정보로, 블로그 제목, 설명, 베이스 URL, 타임존, 작성자 정보, 소셜 미디어 링크, 테마 설정 등을 포함함
- **페이지 (Page)**: 포스트가 아닌 정적 콘텐츠 페이지(About, Archives 등). 네비게이션 메뉴를 통해 접근 가능하며 독립적인 URL을 가짐

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 블로그 초기 설정부터 첫 배포까지 사용자가 2시간 이내에 완료할 수 있음
- **SC-002**: 새 포스트 작성 후 GitHub에 푸시하면 2분 이내에 라이브 사이트에 반영됨
- **SC-003**: 블로그는 모바일, 태블릿, 데스크톱 기기에서 레이아웃이 깨지지 않고 정상 표시됨
- **SC-004**: 포스트 개수가 50개 이상일 때도 홈페이지 로딩 시간이 3초 이내임
- **SC-005**: 검색 기능을 통해 0.5초 이내에 검색 결과를 표시함
- **SC-006**: 다크모드와 라이트모드 전환이 즉시(0.3초 이내) 이루어지며 UI가 깨지지 않음
- **SC-007**: 포스트 본문에 포함된 코드 블록이 10개 이상의 프로그래밍 언어에 대해 Syntax Highlighting을 지원함
- **SC-008**: 블로그 방문자가 3번의 클릭 이내에 원하는 카테고리 또는 태그의 포스트 목록에 도달할 수 있음
- **SC-009**: 사용자가 선택한 테마 설정(라이트/다크)이 브라우저를 닫았다 다시 열어도 유지됨
- **SC-010**: GitHub Actions 빌드 성공률이 95% 이상이며, 실패 시 오류 원인을 로그에서 명확히 확인 가능함
- **SC-011**: 포스트 작성자가 Markdown 문법 가이드 없이도 기본적인 서식(제목, 링크, 이미지, 코드)을 직관적으로 사용할 수 있음
- **SC-012**: RSS 피드를 통해 블로그 업데이트를 구독하는 사용자가 새 포스트 발행 후 1시간 이내에 알림을 받음
